menu_book 使用说明

  1. 粘贴 docker-compose.yml（含 services 段），诊断区会逐项列出解析错误与提示：缺 image 的服务会报错且不生成 YAML；超子集字段（build/networks/secrets 等）逐项列出，未静默丢弃。
  2. 字段映射口径：「8080:80」→ Deployment containerPort 80，Service type NodePort（port/targetPort=80、nodePort=8080）；无 published 端口的服务 → Service type ClusterIP；挂载 → volumeMounts＋volumes hostPath 原样（生产请改 PVC）；环境变量 → env 列表、值一律加引号；depends_on 仅记录不生成 initContainer。
  3. 多服务时点服务名 chip 切换，双标签页分别预览 Deployment 与 Service；「复制当前标签页」复制正在看的那份，「合并下载全部」把所有服务的两份 YAML 以 --- 分隔拼成一个文件。
  4. 确认无误后按需下载，kubectl apply 前务必按集群实际调整命名空间、资源限制与探针。

quiz 常见问题

为什么我的 build / networks / healthcheck 没进 YAML？
因为它们不在本工具承诺的常用字段子集内。直接编造 K8s 字段很容易编错语义，所以它们进了诊断列表并逐项列出，你可以在生成的 baseline 上按集群文档手动补，而不是拿到一份看似完整实则不对的配置。
挂载为什么生成了 hostPath？生产能用吗？
compose 的 bind 挂载（如 ./data:/app/data）在 K8s 里最接近的原语就是 hostPath，所以工具原样映射并明确提示：hostPath 仅适合单机/测试，生产环境请改用 PVC（PersistentVolumeClaim），每条挂载的诊断里都有这条提醒。
depends_on 为什么没有生成启动顺序？
K8s 不保证 Pod 启动顺序，depends_on 在 K8s 里没有 1:1 等价物。工具只做记录并提示，如需顺序请手动编排（initContainer/就绪探针），而不是生成一个看似管用实则不保证的配置。
Service 什么时候是 NodePort、什么时候是 ClusterIP？
服务只要有一条 published 端口（如 "8080:80"），Service 就是 NodePort（nodePort=8080）；只有容器端口（如 "3000" 无 published）时就是 ClusterIP，对内访问。
生成的 YAML 能直接 kubectl apply 吗？
能作为起点，但请先按集群调整：replicas 固定为 1、未设 namespace/资源限制/探针，诊断区与真限制里都写明了，apply 前人工复核一遍。
我的 compose 文件会被上传或验证吗？
不会。全部转换在浏览器本地完成，零网络请求；不连 K8s 集群、不验证镜像是否存在，生成的只是文本配置。
